# Лабораторная работа №2 — Nginx и горизонтальное масштабирование

Реализация задания PA2 на основе первой лабораторной из `../lb1`.
Первая лабораторная сохранена без изменений. Стек: .NET 8 Razor Pages,
StackExchange.Redis, Redis и Nginx. Использован разрешённый заданием Docker Compose.

## Архитектура

```text
Браузер → localhost:8080 (Nginx)
                     ├→ app1:5001 ─┐
                     └→ app2:5002 ─┼→ Redis
                        app3:5003 ─┘  (необязательный третий экземпляр)
Все экземпляры используют общий volume shared-keys для защиты форм.
```

Порты 5001 и 5002 доступны напрямую на localhost. В контейнере Nginx
`localhost` указывает на сам Nginx, поэтому upstream использует имена сервисов
`app1` и `app2`. Redis доступен только внутри сети Compose; данные сохраняются
в отдельном volume. Проект Compose называется `rp-lb2` и не затрагивает `lb1`.

## Требования и запуск

Нужен запущенный Docker Desktop с Linux containers и Docker Compose v2.
Для локальных модульных тестов дополнительно нужен .NET SDK 8.
Команды ниже выполнять из папки `lb2`:

```powershell
.\scripts\start.ps1
```

Открыть http://localhost:8080/, затем проверить прямые адреса
http://localhost:5001/ и http://localhost:5002/.
Скрипт собирает образы, запускает Redis и приложения, проверяет готовность,
проверяет конфигурацию Nginx командой `nginx -t` и запускает прокси.
Сначала прогревается первый экземпляр, чтобы создать общий ключ защиты форм.
Скрипты вычисляют пути относительно своего расположения и работают из любой папки.

```powershell
.\scripts\stop.ps1
```

Остановка удаляет контейнеры и сеть проекта, но сохраняет данные Redis и ключи.
Повторная отправка текста после перезапуска по-прежнему считается дубликатом.
При неудачном запуске скрипт возвращает ошибку; уже запущенные компоненты можно
остановить тем же `stop.ps1`.

Имя и группу для About указать в `Valuator/appsettings.json`, поля
`Author:Name` и `Author:Group`, затем повторить запуск со сборкой.

## Балансировка и добавление экземпляров

```powershell
# По очереди, round-robin — режим по умолчанию
.\scripts\start.ps1 -Method round_robin
.\scripts\test.ps1 -Method round_robin

# Выбор сервера с наименьшим числом активных соединений
.\scripts\start.ps1 -Method least_conn
.\scripts\test.ps1 -Method least_conn

# Привязка по IP клиента
.\scripts\start.ps1 -Method ip_hash
.\scripts\test.ps1 -Method ip_hash

# Третий экземпляр на 5003
.\scripts\start.ps1 -Method round_robin -ThirdInstance
.\scripts\test.ps1 -Method round_robin -ThirdInstance

# Вернуться к двум экземплярам
.\scripts\start.ps1
```

Метод задаётся подключаемым конфигурационным файлом в `nginx/conf`.
Скрипт пересоздаёт Nginx для применения нового метода и списка серверов.
Вариант с третьим экземпляром включает сервис `app3` и файл `three.conf`.
Для четвёртого экземпляра аналогично добавить сервис на 5004 и строку upstream.

Посмотреть распределение запросов можно по заголовку `X-Valuator-Instance`:

```powershell
1..12 | ForEach-Object {
    (Invoke-WebRequest http://localhost:8080/health -UseBasicParsing).Headers['X-Valuator-Instance']
}
docker compose logs nginx
```

Ожидаемое поведение (не результаты выполненного здесь эксперимента):

| Режим | Ожидание |
| --- | --- |
| round_robin | Запросы распределяются между доступными экземплярами |
| least_conn | При параллельной нагрузке предпочтение менее занятому серверу; короткие последовательные запросы могут выглядеть как round-robin |
| ip_hash | Один клиент обычно попадает на один экземпляр; за NAT несколько клиентов могут иметь один видимый IP |
| три экземпляра | В заголовках появляются app1, app2 и app3 |

## Эксперимент с отказом

```powershell
.\scripts\start.ps1
.\scripts\test.ps1 -TestFailover
```

Скрипт останавливает app1, проверяет доступность через Nginx и сохранённый
результат, затем восстанавливает app1 в блоке finally. Nginx использует пассивную
проверку отказов (`max_fails=1`, `fail_timeout=5s`) и повтор GET на другом сервере.
Возвращение экземпляра в балансировку может занять несколько секунд.

Ручной вариант:

```powershell
docker compose stop app1
Invoke-WebRequest http://localhost:8080/health -UseBasicParsing
docker compose start app1
```

При остановке обоих экземпляров (если третий выключен) Nginx не сможет обслужить
запрос и вернёт ошибку 502/504. Общий Redis остаётся единой точкой отказа:
эта работа масштабирует веб-часть, а не базу данных.
Повтор POST после передачи запроса приложению намеренно не включён через
`non_idempotent`, чтобы сбой не приводил к незаметной повторной записи текста.

## Проверки

```powershell
dotnet test ds-2024.sln --configuration Release
.\scripts\test.ps1
```

Модульные тесты проверяют подсчёт символов из PA1 и расшифровку токена другим
экземпляром с общими ключами. Redis-тест из PA1 пропускается, если не задан
`VALUATOR_TEST_REDIS`; он предназначен для отдельно доступного тестового Redis.
Основная проверка контейнерного стенда — `scripts/test.ps1`, она проверяет:

- прямую доступность экземпляров и распределение запросов через Nginx;
- GET формы на 5001 и POST с тем же antiforgery-токеном на 5002;
- чтение одного результата с обоих экземпляров;
- similarity=0 для уникального текста и similarity=1 для повторной отправки;
- опционально доступность после остановки app1 и восстановление контейнера.

Тест оставляет несколько текстов с уникальными идентификаторами в учебной базе.
Ключи защиты форм хранятся в общем Docker volume; это локальный учебный стенд.
Маршрут `/health` подтверждает работу процесса, а не доступность Redis.

При подготовке решения: сборка и модульные тесты выполнены локально;
Docker/Redis/Nginx в окружении отсутствовали, поэтому контейнерный запуск,
`nginx -t`, проверки балансировки и отказа необходимо выполнить командами выше.

## Основные файлы

- `compose.yaml` — Redis, два основных экземпляра, третий по профилю и Nginx.
- `nginx/conf/nginx.conf` — reverse proxy на 8080, upstream и параметры отказов.
- `scripts/start.ps1`, `scripts/stop.ps1` — автоматизация управления системой.
- `scripts/test.ps1` — проверка работающего стенда и эксперимент с отказом.
- `Valuator/Program.cs` — общее хранилище ключей и имя приложения Data Protection,
  диагностический заголовок экземпляра и маршрут `/health`.
- `Valuator/Services` — расчёт и атомарное сохранение результатов из PA1.
